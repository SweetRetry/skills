# 产品需求文档编写规范

帮助用户基于设计稿或产品构想编写高效、可执行的产品需求文档。

## 工作流程

当用户要求编写 PRD 时：

1. **先理解问题** — 明确要解决的核心问题和为什么是现在
2. **定义成功标准** — 协助确定可衡量的成功指标
3. **聚焦交互与逻辑** — PRD 描述「做什么」和「怎么交互」，不描述「长什么样」
4. **穷尽异常** — 主动识别并列出所有异常场景和处理方式

## 写作原则

### 以问题和上下文开篇
最重要的部分是：背景是什么？问题是什么？为什么重要？为什么是现在？在讨论方案之前让团队对齐「为什么」。

### 保持轻量可执行
只保留确保团队对齐的最小必要上下文，聚焦关键结果而非面面俱到的细节。

### 交互优先，视觉分离
PRD 只负责定义功能逻辑、交互行为、数据字段和异常处理。视觉设计（颜色、字体、图标、间距、动效等）由独立的 UI 设计规范承载，PRD 中不涉及。

### 活文档持续迭代
基于生产环境中发现的失败模式持续更新需求，将 PRD 视为随评估结果演进的活文档。

## 文档结构模板

PRD 应包含以下章节（按序排列），所有标题仅使用中文：

### 1. 需求变更记录

- 表格形式：版本号 | 日期 | 变更内容 | 变更人
- 首次编写时填写 V1.0，后续每次修改递增版本号
- 记录每次变更的关键内容摘要

### 2. 名词解释

- 当文档中存在**新概念、模糊性概念、复杂性概念**时，必须提供名词解释
- 目的：降低后续文档的阅读理解成本，确保团队对关键术语理解一致
- 表格形式：术语 | 解释
- 判断标准：
  - 该术语是本产品/本次需求新引入的 → 需要解释
  - 该术语在团队内可能存在歧义 → 需要解释
  - 该术语涉及复杂业务逻辑 → 需要解释
  - 该术语是行业通用且团队已有共识 → 无需解释

### 3. 需求背景及目标

通过数据、调研或商业策略推演的关键结论，阐述清楚本次需求的业务价值，及期望本次需求可以达成的业务目标。衡量业务价值可以从**业务增长**或**降本增效**方向切入。

必须包含以下三个子章节：

- **3.1 需求背景**：阐述清楚用户/竞品调研的结论，或数据分析结论。说明当前痛点、市场机会或业务瓶颈
- **3.2 解决路径**：描述基于关键结论和本次需求之间的关系，说明解决路径和产品策略
- **3.3 业务目标**：描述本次需求期望解决的具体问题或者符合 SMART 原则的业务目标

补充说明：
- 目标用户：谁会使用，用户画像
- 本期范围：明确包含的功能
- 不在本期：明确排除的功能，防止范围蔓延

### 4. 产品架构

根据需求规模选择不同粒度：

**中大需求**（涉及多模块/多角色/多系统交互）须提供：
- **用例图**：梳理不同角色的操作流程和具体事项，明确每个独立系统需要多少个 story 点及需要做什么
- **系统架构**：系统间的依赖和数据流向
- **功能架构**：功能模块的划分和层级关系
- **信息架构**：页面结构概览、区域划分和层级关系

**小需求**可以仅展示：
- 当前页面的信息架构内容（ASCII 布局图或层级列表）

**注意**：架构图中**不描述**颜色、字体、图标名称、间距、圆角等视觉参数。

### 5. 功能模块详述

#### 5.1 核心流程

- 作为功能模块详述的**第一个部分**，优先呈现
- 使用**结构化编号步骤列表**描述用户完成核心任务的主流程（不使用 Mermaid 流程图，确保飞书兼容）
- 格式规范：
  - 每步使用阿拉伯数字编号（1. 2. 3. ...）
  - 决策节点使用 `**判断**：条件？` 格式，分支用缩进无序列表展开
  - 每个分支以 `**选项** →` 开头，描述后续动作
  - 循环用「回到步骤 X」表示
- 涵盖正常路径和主要异常路径

#### 5.2 各功能模块

按模块逐一描述，每个模块包含：

**功能说明**：该模块做什么

**字段规格**：表格列出字段名、类型、必填/选填、校验规则、默认值

**交互行为**（使用无序列表）：
- 每条交互行为用「用户操作 → 系统响应」的格式描述
- 包含成功路径和失败路径
- 示例格式：
  - 用户点击「提交」按钮 → 系统校验表单字段，校验通过后提交数据并显示成功提示
  - 用户点击「提交」按钮但字段校验失败 → 系统在对应字段下方显示校验错误提示

**状态流转**：该模块涉及的状态变化（Mermaid 状态图或流程图）

**交互规则**（跟随在对应模块下）：
- 该模块特有的交互约束和规则
- 无序列表形式列出

**异常场景**（跟随在对应模块下）：
- 该模块可能出现的异常场景和对应处理方式
- 无序列表形式：异常场景 → 处理方式 → 用户可见反馈

### 6. 弹窗与浮层

每个弹窗/浮层包含：
- 触发条件
- 字段规格（表格）
- 操作按钮与行为（无序列表）
- 关闭条件
- 交互规则（无序列表，跟随在对应弹窗下）
- 异常场景（无序列表，跟随在对应弹窗下）

### 7. 待确认问题

使用 Q&A 格式呈现，便于相关方直接编辑补充：

```
**Q1**：[问题描述]
**建议方案**：[如有建议方案则填写]
**A**：[待填写 / 已确认的结论]
**确认人**：[待填写]
**确认日期**：[待填写]

**Q2**：[问题描述]
**建议方案**：[如有建议方案则填写]
**A**：[待填写 / 已确认的结论]
**确认人**：[待填写]
**确认日期**：[待填写]
```

## 写作禁令

以下内容 **禁止出现** 在 PRD 中：

- ❌ 图标名称或图标库引用（如 `book-open`、`chevron-left`、`lucide`）
- ❌ 颜色值或设计 Token（如 `$accent-purple`、`#22C55E`、紫色实心）
- ❌ 字体参数（如 `fontSize: 13`、`fontWeight: 600`、`Inter`）
- ❌ 间距/尺寸/圆角等排版参数（如 `padding: 16px`、`gap: 8`、圆角 10px）
- ❌ 排版样式描述（如「浅色文字，行高 1.7」「灰色描边按钮」）
- ❌ 英文章节标题（如 `In Scope`、`Out of Scope`，应写「本期范围」「不在本期」）
- ❌ 设计 Token 参考章节（整个章节不需要）
- ❌ 具体的空状态/错误状态的界面文案内容（文案由 UX Writing 单独管理）
- ❌ 独立的「全局交互规则」和「异常与边界处理」汇总章节（交互规则和异常场景应跟随在对应的功能模块下）

## 写作要求

以下内容 **必须包含**：

- ✅ 每个字段的类型、必填性、校验规则和边界值
- ✅ 每个用户操作对应的系统响应（含成功和失败路径），使用无序列表格式
- ✅ 所有状态之间的流转条件和流转图
- ✅ 权限控制（如果有）
- ✅ 数据依赖关系（哪些数据来自上游模块，哪些传递给下游）
- ✅ 并发/竞态场景处理（如适用）
- ✅ 空状态的触发条件和可执行操作（不描述视觉表现）
- ✅ 加载状态和超时处理策略
- ✅ 分页/无限滚动策略（如适用）
- ✅ 交互规则和异常场景必须跟随在对应的功能模块/弹窗下，不单独汇总
- ✅ 核心流程作为功能模块详述的第一个部分呈现
- ✅ 待确认问题使用 Q&A 格式，包含建议方案、确认人、确认日期字段

## 从设计稿提取时的注意事项

当基于 Pencil 等设计工具的 .pen 文件编写 PRD 时：

1. **提取功能逻辑**，忽略视觉实现 — 读节点结构理解功能模块，不搬运颜色/字体/间距
2. **提取字段定义** — 从输入框 placeholder、表单标签等推断字段规格
3. **提取状态变化** — 从多个页面状态（如 `已解析`/`解析中`/`解析失败`）推断状态机
4. **提取交互模式** — 从组件结构（如 Tab、弹窗、抽屉）推断交互行为
5. **主动补充异常** — 设计稿通常只展示正常路径，PRD 需要补充异常路径

## 引导问题

- 这个功能解决什么问题？为什么现在做？
- 如何衡量功能是否成功？哪个指标会变化？
- 用户是谁？功能上线后他们的工作流有什么变化？
- 什么是明确不做的？
- 还有哪些关键决策待定？

## 常见错误

- **从方案开始写** — 应先写问题和背景
- **没有成功标准** — 必须有可量化的衡量方式
- **搬运视觉设计** — PRD 不是设计标注文档
- **只写正常路径** — 异常处理同等重要
- **缺少「为什么是现在」** — 没有紧迫性说明，优先级会被质疑
- **交互规则和异常场景脱离上下文** — 应跟随在对应模块下，而非独立汇总章节
- **待确认问题只列问题不留回填空间** — 应使用 Q&A 格式便于协作编辑
