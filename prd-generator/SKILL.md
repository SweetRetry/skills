# PRD Generator - 产品需求文档生成器

## 概述

PRD Generator 帮助产品经理快速创建、修改和优化符合行业标准的产品需求文档 (Product Requirements Document)。本技能基于成熟的 PRD 模板和最佳实践,确保文档结构完整、逻辑清晰、信息准确。

**核心能力:**
- **从零创建:** 基于产品想法或功能描述生成完整的 PRD
- **原型转文档:** 解析 HTML/Figma 原型图,自动生成结构化需求文档
- **文档优化:** 修改、补充、完善现有 PRD,确保符合规范
- **模板定制:** 根据项目特点调整文档结构和章节内容

## 工作流决策树

当用户请求 PRD 相关任务时,按照以下决策树选择工作流:

```
用户请求 PRD 任务
    │
    ├─ 用户提供了原型图文件? (HTML/Figma链接)
    │  └─ YES → 使用【原型图转 PRD 流程】
    │
    ├─ 用户提供了现有 PRD 文件? (.docx/.md/.pdf)
    │  └─ YES → 使用【修改现有 PRD 流程】
    │
    ├─ 用户描述了具体功能/模块?
    │  └─ YES → 使用【创建新 PRD 流程】
    │
    └─ 用户仅提供了模糊需求?
       └─ 先询问以下问题,收集信息后再选择流程:
          1. 这是新功能还是修改现有功能?
          2. 是否有原型图或设计稿?
          3. 目标用户和核心痛点是什么?
          4. 优先级和预期上线时间?
```

## 创建新 PRD 流程

### 步骤 1: 收集需求信息

在开始撰写前,通过提问收集必要信息:

**必问问题:**
1. **项目背景:** 这是什么产品/功能?解决什么问题?
2. **目标用户:** 主要面向哪些用户群体?
3. **核心痛点:** 用户当前遇到的最大困扰是什么?
4. **功能范围:** 本次需求包含哪些主要功能模块?
5. **优先级:** P0 (必须有) / P1 (应该有) / P2 (可以有) 如何划分?

**选问问题 (根据项目类型):**
- 是否有竞品参考?有哪些值得借鉴的点?
- 是否有技术限制或依赖?
- 预期的性能指标是什么? (响应时间、并发量等)
- 是否需要考虑多端适配? (PC/移动/平板)

### 步骤 2: 选择文档结构

根据需求类型选择合适的模板结构:

**标准 PRD 结构** (适用于大多数功能):
- 一、需求变更记录
- 二、名词解释
- 三、需求背景及目标
- 四、产品架构
- 五、需求清单
- 六、功能详细说明
- 七、非功能需求
- 八、技术实现说明 (可选)
- 九、附录 (可选)

**简化 PRD 结构** (适用于小功能迭代):
- 一、需求背景
- 二、功能清单
- 三、功能详细说明
- 四、数据埋点

**复杂 PRD 结构** (适用于大型项目):
- 在标准结构基础上增加:
  - 信息层级策略
  - 多角色权限矩阵
  - 数据流转图
  - 状态机设计

### 步骤 3: 撰写文档

按照以下优先级顺序撰写各章节:

**第一轮 - 核心框架 (必写):**
1. **需求背景及目标** - 说明"为什么做"
2. **功能架构** - 展示"做什么"的全貌
3. **需求清单** - 列出所有功能点和优先级

**第二轮 - 详细说明 (必写):**
4. **产品流程图** - 描述用户操作路径
5. **信息说明** - 定义每个字段的来源和规则
6. **按钮说明** - 说明每个交互的触发逻辑

**第三轮 - 补充完善 (选写):**
7. **异常逻辑** - 考虑边界情况和错误处理
8. **性能要求** - 明确可量化的性能指标
9. **技术实现说明** - 复杂功能的技术方案选型

### 步骤 4: 质量检查

撰写完成后,执行以下检查清单:

- [ ] 所有表格格式正确,列对齐
- [ ] 需求清单中的功能点在详细说明中都有对应章节
- [ ] 所有字段都明确了数据来源
- [ ] 所有按钮都说明了触发逻辑
- [ ] 考虑了异常情况和边界条件
- [ ] 性能指标具体可量化
- [ ] 专业术语都在名词解释中定义

### 步骤 5: 交付文档

将文档以 Markdown 格式输出,并说明:
- 文档版本号
- 建议的文件命名 (如: `【项目名】模块名_PRD_v1.0.md`)
- 下一步行动 (如需要补充原型图、需要技术评审等)

## 修改现有 PRD 流程

### 步骤 1: 分析现有文档

首先读取并分析用户提供的 PRD 文件:

```
如果是 .docx 文件:
  → 提示用户:"由于 .docx 是二进制格式无法直接读取,请将文档转换为 .md 或 .pdf 格式后重新上传,
     或者直接告诉我需要修改的具体内容。"

如果是 .md 或 .pdf 文件:
  → 使用 Read 工具读取文件内容
  → 分析文档结构:是否符合标准 PRD 格式?
  → 识别缺失章节:哪些必要章节没有?
  → 标记问题区域:信息不完整、逻辑不清晰的部分
```

### 步骤 2: 明确修改需求

询问用户具体的修改意图:

1. **补充型修改** - 添加缺失的章节或字段
   - "我发现文档缺少【XX章节】,是否需要补充?"
   - 示例:缺少"异常逻辑"、"数据埋点"、"性能要求"

2. **优化型修改** - 改进现有内容的质量
   - "【XX章节】的描述不够具体,是否需要细化?"
   - 示例:流程图过于简化、字段说明不明确

3. **调整型修改** - 根据新需求变更内容
   - "请告诉我具体需要调整哪些功能点?"
   - 示例:增加新功能、删除废弃功能、修改交互逻辑

### 步骤 3: 执行修改

根据修改类型选择策略:

**补充缺失章节:**
- 使用模板中的标准章节结构
- 根据现有内容推断缺失信息
- 用【待补充】标记需要用户确认的部分

**优化现有内容:**
- 保持原有结构和格式风格
- 将简单描述扩展为结构化表格
- 将模糊说明改为明确规则

**调整功能内容:**
- 先标记变更部分 (用删除线和高亮)
- 更新需求清单的优先级
- 同步更新相关章节 (流程图、字段说明等)

### 步骤 4: 输出修改后文档

提供两种输出方式:

1. **完整文档** - 输出修改后的完整 PRD
2. **变更摘要** - 仅输出修改的部分,并说明:
   - 修改位置 (章节名称)
   - 修改内容 (新增/删除/调整)
   - 修改原因

## 原型图转 PRD 流程

### 步骤 1: 解析原型图

根据原型图类型选择解析方式:

**HTML 原型图:**
```
1. 使用 Read 工具读取 HTML 文件
2. 分析页面结构:
   - 识别主要模块 (header/sidebar/main/footer)
   - 提取表单字段 (input/select/textarea)
   - 识别按钮和链接 (button/a)
   - 分析交互逻辑 (JavaScript 事件绑定)
3. 提取关键信息:
   - 页面标题和导航结构
   - 数据展示字段列表
   - 表单输入项和验证规则
   - 按钮触发的操作
```

**Figma 链接:**
```
1. 提示用户:"Figma 链接需要权限访问,请提供以下信息:
   - 页面截图 (可直接粘贴)
   - 或者描述原型图的主要功能模块"
2. 根据用户提供的截图或描述进行分析
```

### 步骤 2: 提取功能点

从原型图中系统化地提取需求:

**页面级功能:**
- 列出所有页面/Tab (如:"首页"、"项目管理"、"开始创作")
- 每个页面的核心功能 (查看、创建、编辑、删除等)

**组件级功能:**
- 表单字段 → 转换为"信息说明"表格
- 按钮 → 转换为"按钮说明"表格
- 列表/卡片 → 转换为"数据展示"说明

**交互级功能:**
- 点击事件 → 转换为"产品流程图"
- 状态变化 → 转换为"状态机"描述
- 弹窗/抽屉 → 转换为"交互说明"

### 步骤 3: 生成 PRD 框架

基于提取的功能点自动生成文档框架:

```markdown
## 四、产品架构

### 功能架构
[根据页面结构自动生成树状图]

### 信息架构
[根据页面布局自动生成布局描述]

## 五、需求清单
[根据提取的功能点自动生成表格,优先级默认 P0]

## 六、功能详细说明

### 信息说明
[根据表单字段自动生成字段表格]

### 按钮说明
[根据按钮和链接自动生成触发逻辑表格]
```

### 步骤 4: 补充缺失信息

原型图无法提供的信息需要询问用户:

**必须补充:**
- 需求背景:为什么要做这个功能?
- 数据来源:每个字段的数据从哪里来?
- 异常逻辑:边界情况如何处理?

**建议补充:**
- 性能要求:响应时间、加载速度等
- 权限控制:谁可以访问、谁可以操作
- 数据埋点:需要监控哪些用户行为

## 撰写规范和最佳实践

### 1. 语言风格

- **简洁明确:** 避免冗长描述,使用结构化表格组织信息
- **主动语态:** 使用"用户可..."、"系统应..."而非被动语态
- **量化目标:** 用具体数字代替模糊描述 (如"响应时间 ≤ 500ms"而非"快速响应")

### 2. 表格使用

**字段说明表格必须包含:**
```markdown
| 字段 | 数据来源 | 是否可编辑 | 控件类型 | 说明 |
```

**按钮说明表格必须包含:**
```markdown
| 按钮 | 位置 | 触发条件 | 触发内容 | 触发结果 |
```

### 3. 流程图格式

使用文本树状图,清晰展示逻辑分支:

```
开始:用户进入页面
    │
    ▼
步骤1:加载数据
    │
    ├──► 分支A:数据为空
    │    └── 显示空状态
    │
    └──► 分支B:数据正常
         └── 渲染列表
```

### 4. 优先级定义

- **P0 (必须有):** 核心功能,无此功能产品无法上线
- **P1 (应该有):** 重要功能,显著提升用户体验
- **P2 (可以有):** 锦上添花,资源充足时实现

### 5. 异常处理

每个主要功能都应考虑:
- 数据为空时如何展示
- 网络请求失败如何处理
- 用户输入非法时如何提示
- 权限不足时如何拦截

## 常见问题处理

### Q1: 用户提供的信息不完整怎么办?

**策略:** 分阶段输出,标记待补充内容

```markdown
## 三、需求背景及目标

### 1. 需求背景及价值

**用户痛点:**
- 【待补充:请描述用户当前遇到的主要问题】

**核心价值:**
- 【待补充:解决上述痛点后带来的价值】
```

输出后提示:"文档框架已生成,【待补充】部分需要你提供更多信息。"

### Q2: 用户要求参考竞品功能怎么办?

**策略:**
1. 询问竞品名称或截图
2. 分析竞品功能点
3. 在 PRD 中新增"竞品分析"章节 (附录形式)
4. 将可借鉴的点整合到功能设计中

### Q3: 用户要求生成多个模块的 PRD 怎么办?

**策略:** 拆分为独立文档

```
建议将【项目名】的需求拆分为以下独立 PRD:
1. 【项目名】登录注册模块_PRD
2. 【项目名】项目管理模块_PRD
3. 【项目名】内容创作模块_PRD

每个文档独立维护,便于评审和追溯。是否需要我逐个生成?
```

### Q4: 用户要求转换为 Word 格式怎么办?

**策略:**
1. 提示:"我生成的是 Markdown 格式,你可以通过以下方式转换为 Word:
   - 使用 Pandoc 工具:`pandoc input.md -o output.docx`
   - 使用在线转换工具:如 Markdown to Word Converter
   - 复制到 Word 后手动调整格式"
2. 确保 Markdown 格式规范,便于转换

## 输出检查清单

每次生成或修改 PRD 后,执行以下检查:

**结构完整性:**
- [ ] 文档头部信息完整 (版本、日期、模块名)
- [ ] 必要章节齐全 (背景、架构、清单、详细说明)
- [ ] 表格格式正确,列对齐

**内容准确性:**
- [ ] 所有字段明确数据来源
- [ ] 所有按钮明确触发逻辑
- [ ] 优先级定义清晰 (P0/P1/P2)

**逻辑严密性:**
- [ ] 需求清单与详细说明一一对应
- [ ] 流程图覆盖主要场景和异常分支
- [ ] 考虑了边界条件和错误处理

**可读性:**
- [ ] 专业术语在名词解释中定义
- [ ] 使用列表和表格而非长段落
- [ ] 关键信息使用加粗或标记
